# Backend — лабораторная №2

FastAPI + PostgreSQL + SQLAlchemy. Все команды ниже выполняются в PowerShell из папки `backend`, кроме отдельно отмеченной настройки PostgreSQL.

## 1. Подготовить программы

Нужны Python 3.12 или новее и PostgreSQL 18. При установке PostgreSQL сохраните пароль пользователя `postgres`. Убедитесь, что локальный сервер PostgreSQL запущен.

## 2. Создать пользователя и базу

Откройте SQL Shell (psql), подключитесь к локальному серверу под `postgres`. Либо запустите psql из PowerShell:

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h 127.0.0.1 -U postgres -d postgres
```

В psql последовательно выполните:

```sql
CREATE ROLE car_damage LOGIN;
\password car_damage
CREATE DATABASE car_damage OWNER car_damage;
\q
```

Команда `\password` дважды запросит новый пароль для роли приложения. Запомните его: он понадобится в `.env`. Это команды однократной подготовки, повторять их для уже существующей базы не нужно.

## 3. Установить зависимости

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```
## 4. Настроить подключение

```powershell
Copy-Item .env.example .env
```

Откройте `.env` и замените `DB_PASSWORD` паролем роли `car_damage`. Пример содержит только заглушку. При необходимости измените адрес, порт, имя базы и пользователя.

| Переменная | Назначение |
| --- | --- |
| `DB_HOST` | Адрес PostgreSQL, по умолчанию `127.0.0.1` |
| `DB_PORT` | Порт PostgreSQL, по умолчанию `5432` |
| `DB_NAME` | Имя базы приложения |
| `DB_USER` | Роль для подключения |
| `DB_PASSWORD` | Пароль этой роли |

Для пароля с `#`, пробелами или другими специальными символами используйте кавычки в `.env`. Строка подключения собирается через `URL.create`, поэтому вручную кодировать пароль для URL не требуется. Переменные окружения имеют приоритет над `.env`. Реальный `.env` исключён из Git.

## 5. Создать таблицы

```powershell
.\.venv\Scripts\python.exe -m app.init_db
```

Используется `Base.metadata.create_all`. Повторный запуск не удаляет существующие записи. Этот способ создаёт отсутствующие таблицы, но не меняет структуру уже созданных.

## 6. Запустить API

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Откройте [Swagger](http://127.0.0.1:8000/docs). 
Запуск приложения сам по себе не создаёт таблицы. Если база недоступна или таблицы ещё не созданы, запросы к данным возвращают 503 с понятным сообщением.

## Модель данных

| Таблица | Поля |
| --- | --- |
| `users` | `id` PK; `name` до 80 символов; уникальный `email` до 254 символов; `created_at` |
| `cars` | `id` PK; `user_id` FK → `users.id`; `brand`, `model` до 60 символов; целочисленный `year`; необязательный `body` |
| `inspections` | `id` PK; `car_id` FK → `cars.id`; `photo_name` до 255 символов; необязательное `notes` до 2000 символов; `created_at` |

Идентификаторы создаёт PostgreSQL. Даты создания заполняются сервером базы, имеют часовой пояс и не редактируются через API. Внешние ключи индексируются. При удалении родителя используется `ON DELETE CASCADE`.

Email приводится к нижнему регистру перед сохранением и проверкой уникальности. Имя, марка и модель не могут состоять из пробелов. Год передаётся JSON-числом от 1900 до текущего года. На frontend год пока строковый: при будущей интеграции потребуется преобразование в число.

Тип кузова: `Седан`, `Хэтчбек`, `Универсал`, `Кроссовер`, `Внедорожник`, `Купе`, `Минивэн`, `Пикап`, `Другой` или `null`.

`photo_name` содержит только имя файла с расширением JPG, JPEG, PNG или WebP. Это метаданные, а не загрузка или проверка содержимого изображения. `/` и `\` в имени запрещены. Размер файла через этот API не проверяется, поскольку сам файл не передаётся.

## Маршруты

Для каждого ресурса `users`, `cars`, `inspections`:

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/ресурс` | Создать, 201 и созданная запись |
| GET | `/api/ресурс` | Список, 200 |
| GET | `/api/ресурс/{id}` | Одна запись, 200 или 404 |
| PUT | `/api/ресурс/{id}` | Полное обновление, 200 |
| DELETE | `/api/ресурс/{id}` | Удалить, 204 без тела |

PUT принимает те же поля, что и POST. Это полная замена редактируемых данных: обязательные поля нужно передать заново, пропущенные необязательные поля становятся `null`. `id` и `created_at` не меняются. Лишние поля запрещены.

Списки отсортированы по `id`. Параметры `offset` (от 0) и `limit` (от 1 до 100, по умолчанию 20) позволяют получать данные частями. Автомобили можно отфильтровать по `user_id`, осмотры — по `car_id`. Фильтр по отсутствующему родителю возвращает пустой список.

Примеры: `/api/cars?user_id=1`, `/api/inspections?car_id=1`, `/api/users?offset=0&limit=10`.

## Проверка вручную
В Swagger раскройте метод, нажмите `Try it out`, укажите JSON и нажмите `Execute`. Используйте реальные `id` из ответов, а не полагайтесь на значение 1.

1. Создайте пользователя через `POST /api/users`:

```json
{
  "name": "Михаил",
  "email": "mikhail@example.com"
}
```

2. Создайте автомобиль через `POST /api/cars`, подставив полученный `user_id`:

```json
{
  "user_id": 1,
  "brand": "Toyota",
  "model": "Camry",
  "year": 2018,
  "body": "Седан"
}
```

3. Создайте осмотр через `POST /api/inspections`, подставив `car_id`:

```json
{
  "car_id": 1,
  "photo_name": "car.jpg",
  "notes": "Автомобиль сфотографирован целиком"
}
```

4. Получите списки и отдельные записи через GET. Измените записи через PUT и снова получите их. Перезапустите backend: записи должны остаться в PostgreSQL.
5. Проверьте ошибки: неверная почта, год 1899 или будущий год — 422; повторная почта — 409; несуществующий автомобиль или пользователь — 404.
6. Удалите осмотр и проверьте, что автомобиль остался. Создайте осмотр снова; удалите автомобиль и убедитесь, что осмотр исчез, а пользователь остался. Для проверки удаления пользователя создайте новую цепочку и удалите пользователя: связанные записи тоже исчезнут.

Посмотреть данные непосредственно в PostgreSQL можно через pgAdmin или psql, подключившись к базе `car_damage`:

```sql
SELECT * FROM users ORDER BY id;
SELECT * FROM cars ORDER BY id;
SELECT * FROM inspections ORDER BY id;
```

## Ответы об ошибках

- 404 — нужная запись или родитель не найдены.
- 409 — почта уже занята или возник конфликт ограничений базы.
- 422 — некорректные поля, параметры пути или JSON.
- 503 — не удалось выполнить запрос к PostgreSQL.

Пример ошибки валидации:

```json
{
  "detail": "Проверьте данные запроса",
  "errors": [{"field": "body.year", "message": "Значение должно быть не меньше 1900"}]
}
```

## Автоматические тесты
```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:TEST_DB_NAME = 'car_damage_test'
.\.venv\Scripts\python.exe -m pytest -q
```
Remove-Item Env:TEST_DB_NAME для удаления 

Остальные параметры подключения берутся из `.env`. Имя тестовой базы обязательно должно заканчиваться на `_test`. Для каждого теста создаётся отдельная схема со случайным именем; после теста удаляется только эта схема. Таблицы приложения не очищаются.

Проверяются CRUD, сохранение через отдельную сессию БД, ошибки валидации, уникальность почты, отсутствующие родители, фильтры и каскадное удаление через API и непосредственно в PostgreSQL.
